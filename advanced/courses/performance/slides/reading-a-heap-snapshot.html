Reading a heap snapshot

  1. Snapshot → repeat a navigation → snapshot
  2. Class filter: a component, or Detached
  3. Count grows with every navigation? That's a leak
  4. Retainers: what keeps it alive? Watch out for SetInterval, SetTimeout and unsubscribed RxJS.

Held by DevTools console? Not your app.

The tool for exercise 4, before they leave. DevTools, Memory, Heap snapshot, Take snapshot. Click through the four lines, then the trap. Here's how you read the Memory panel, because in the exercise you're on your own with it. Click. Open DevTools, Memory, pick Heap snapshot and take one. Then do the navigation you suspect, a fixed number of times, and take a second one. A snapshot always collects garbage first, so what's in it is really held. Click. The class filter at the top of the Summary narrows the rows. Type a component's class name and you get its count. Type Detached and you get one row per tag: Detached div, Detached button, and so on. DevTools has no total for all of them, so read the row for an element you know. Click. One count on its own means nothing. A count that grows with every navigation you repeat is a leak. That's why you count your navigations. Click. Open the row, click one object, and the Retainers pane underneath shows the chain of references that keeps it alive. Read it from the bottom: start at something long-lived, like Window or a timer, and follow it up to your object. Click. The trap: if you clicked a node in the Elements panel or logged it, DevTools itself holds on to it, and the retainer says DevTools console. That's not your app. Clear the console, or snapshot from a fresh tab. If you want a quicker look in your own app later: the same panel has a profile type called Detached elements. Today we use the snapshot, because it shows the components too.
