Don't copy state with an effect

The effect runs later, during change detection. Until then, code reads a stale copy

Two sources of truth, an extra change detection pass, and a risk of loops

The screen looks fine. The code doesn't

Derived: computed
Derived, but writable: linkedSignal

firstName = signal('Ada');
lastName = signal('Lovelace');

// Derived: always in sync
fullName = computed(() => `${this.firstName()} ${this.lastName()}`);

// Anti-pattern: a copy kept up to date by an effect
fullNameCopy = signal('');
constructor() {
  effect(() =>
    this.fullNameCopy.set(`${this.firstName()} ${this.lastName()}`));
}

rename() {
  this.firstName.set('Grace'); this.lastName.set('Hopper');
  this.fullName();      // 'Grace Hopper'
  this.fullNameCopy();  // still 'Ada Lovelace'
}

Infinite-loop real fix: no effect. addRandomPlayground() would do this.playgrounds.update(p => [...p, getRandomPlayground()]) itself (the comment in infinite-loop.component.ts says so; the demo keeps the effect to show the loop). Ask about their exercise 1: center and markers could be computed. subscribe(x => this.x.set(x)) is the same copy pattern; toSignal fixes it (later today). Now the most common mistake with effects: using one to keep a copy of state in sync. fullName is a computed: always right, the moment you read it. fullNameCopy is a signal an effect keeps updated. In rename we set the names and read both straight away. The computed says Grace Hopper. The copy still says Ada Lovelace, because the effect only runs later, during change detection. The screen looks fine, because by the time it renders the effect has run. The code in between reads stale data. And you have two sources of truth, an extra pass and a risk of loops.
