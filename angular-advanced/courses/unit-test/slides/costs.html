Costs

Learning to write tests takes time. Reflect on your time spent.

A passing test can provide a safety net so it’s easy to change existing code

The time spent fixing and updating unit tests.

Test the minimal amount of code. Over-testing can be costly. 

Fear of changing code that may break a load of unit tests, hence incur extra work

The time spent writing/learning: Maybe set a timer for how long you want to spend unit testing. Learning. The time spent fixing and updating unit tests: Refactoring, someone changed an interface, etc.. The tendency – either by you or your colleagues – to avoid improving and refactoring application code out of fear that it may break a load of unit tests and hence incur extra work Can take some time to get used to writing tests. Therefore it can take longer to develop new features in the beginning. Don’t start with testing the DOM. Start with testing the code. Identify the layers of testing knowledge and start bit by bit to get “the black belt” Cost of trust. Cost of time/money. When there’s a safety net of a passing test (a good one). It’s easy to experiment with changing existing code. Part of becoming a better developer is improving the way you code and that’s a journey. It would be a real shame if what’s stopping you from changing some code is that you’re afraid something would break. Over-testing can be costly. In most cases don’t test the DOM. For example don’t test if a click event calls a specific function in the component. You should determine when something fails because of training experience by the developer who coded it. Test the minimal amount of code. Don’t test private functions for instance.
