Exercise 2 - Bonus: the fix

Keep a signal of ids. Add the id when it is missing, remove it when it is there. favorites.service.ts becomes:

import { Service, signal } from '@angular/core';

@Service()
export class FavoritesService {

  private readonly _favoriteIds = signal<string[]>([]);
  readonly favoriteIds = this._favoriteIds.asReadonly();

  toggle(id: string): void {
    this._favoriteIds.update(ids => ids.includes(id) ? ids.filter(favoriteId => favoriteId !== id) : [...ids, id]);
  }

}

Then add this test to favorites.service.spec.ts. It is green on arrival: the fix already handles it, and the test pins that behavior.

it('should remove a playground from the favorites when toggled again', () => {
  // Arrange
  service.toggle('legeplads.2');
  // Act
  service.toggle('legeplads.2');
  // Assert
  expect(service.favoriteIds()).toEqual([]);
});
Fix: a signal of ids, asReadonly for favoriteIds. Whole class in favorites.service.ts. Toggle-twice test in favorites.service.spec.ts: green on arrival, pins the behavior. A boolean cannot say which playgrounds are favorites. A signal holding the list of ids can: toggle adds the id if it is missing and removes it if it is there. The private signal is _favoriteIds, and favoriteIds is its read-only view, so nobody outside the service can set it. Then add the test where you toggle one id twice and expect an empty list. It is green the moment you write it, because the same implementation already handles it. That is fine: the test pins the behavior, so it turns red if someone breaks the removal.
