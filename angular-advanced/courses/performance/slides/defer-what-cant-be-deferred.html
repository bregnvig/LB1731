What @defer can't split out

  • Used outside the block, even as a viewChild: eager
  • Used by @placeholder, @loading, @error: eager
export class HomeComponent {
  map = viewChild(LeafletComponent);
  ...

// npm run build: Initial total 1.79 MB,
// and no leaflet-component chunk
30 seconds, a list of "don't". viewChild(LeafletComponent) in Home on top of @defer: no leaflet chunk, Initial total 1.79 MB (measured on a copy of the exercise 3 start). Placeholder, loading, error: what they use is eager. Only standalone components, directives and pipes move. SSR renders the placeholder, triggers don't run on the server. The HMR trap (dev server loads every defer chunk up front) is on the exercise 3 "Watch the chunks load" slide. @defer only moves code that nothing else needs at start, and there are a few quiet ways to lose the win. First: if anything outside the block uses the component, it stays eager. Here I deferred the map and added one viewChild of LeafletComponent in Home. The build has no leaflet chunk any more, and Initial total is 1.79 MB, a bit worse than doing nothing. Ask the room: how would you notice that in a code review? You wouldn't. You notice it in the lazy table of the build. Second: what the placeholder, loading and error blocks use is eager too, so keep them cheap. And only standalone things move. In a modern app that's everything, but in an older one with NgModules, check. With server-side rendering the server renders the placeholder and the triggers don't run there.
