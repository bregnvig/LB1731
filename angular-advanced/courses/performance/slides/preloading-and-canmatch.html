Preloading and canMatch

Lazy = first visit waits for the chunk

withPreloading fetches them in the background after start

Custom PreloadingStrategy to pick routes

Guard a lazy route with canMatch: false means the chunk is never downloaded

provideRouter(AppRoutes, withPreloading(PreloadAllModules)),

// a lazy route behind a guard
{
  path: 'admin',
  canMatch: [() => inject(Auth).isAdmin()],
  loadChildren: () => import('./admin/admin.routes'),
},
Lazy means the first navigation to it waits for the chunk. PreloadAllModules: fetch every lazy route after the first render, in the background. Custom PreloadingStrategy for "only these". canMatch, not canLoad: the guard runs before the chunk is fetched. The price of a lazy route is a wait the first time the user goes there. Preloading removes that wait without making the start slower: after the app is up, the router fetches the lazy chunks in the background. withPreloading(PreloadAllModules) is the simple version: everything lazy. If that is too greedy, write your own PreloadingStrategy and pick the routes, for instance with a data flag on the route. The default is NoPreloading. Guards: canLoad is the old guard for lazy routes. Use canMatch. It runs when the router matches the route, so if it returns false the chunk is not downloaded and the router tries the next matching route. That also lets you have two different components for the same path, depending on a condition, like a logged in user.
