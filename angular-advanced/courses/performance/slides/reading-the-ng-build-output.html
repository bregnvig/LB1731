Reading the build output

npm run build prints a table of chunks

Initial: downloaded before the app starts. Lazy: fetched later

Raw size is the file, transfer size is after compression

The line to watch: Initial total

main: 1.53 MB

Initial total: 1.77 MB raw, 383.17 kB transfer

Initial = downloaded before anything shows. Lazy = fetched later (no lazy table yet). Raw is the file, transfer is the estimate after compression. Look at both. This is the exercise 3 starting point: zoneless, nothing lazy. Initial total 1.77 MB / 383.17 kB, main 1.53 MB. Full output, cut from the slide (raw / transfer): main 1.53 MB / 357.12 kB, styles 242.57 kB / 25.55 kB, polyfills 494 bytes / 494 bytes, Initial total 1.77 MB / 383.17 kB. Optional: ng build --stats-json writes stats.json for a bundle analyzer. Before we change anything, we learn to read what the build tells us. npm run build, and look at the table it prints. On the slide are the two lines we care about. The first table is the initial chunk files: everything the browser has to download and run before the app starts. The Initial total line is the number we want to push down. Raw size is the file on disk. Estimated transfer size is what goes over the wire after compression. Users on a slow connection feel the second one; parsing and running cost the first one. Once something is lazy, a second table shows up: lazy chunk files. You'll see it appear in the exercise. Ask the room: main is 1.53 MB. What do you think is in there? Write your guess down, we'll check it after the exercise. The hashes in the file names change between builds. That's fine, it's how the browser cache knows a file is new.
