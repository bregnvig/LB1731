Moving to signals: good and bad

Good

  • No markForCheck: a signal read in a template schedules the update itself
  • No cleanup: toSignal unsubscribes and effect is destroyed with the component
  • computed is lazy and memoised: it only runs when read

Bad

  • effect is eager: it runs even if nobody needs the result
  • toSignal is eager: it subscribes straight away, even if the signal is never read (an HTTP request still goes out)

Use computed for derived values, effect for side effects only.

Good: no markForCheck, no cleanup (injection context destroy), computed lazy + memoised. Bad: effect and toSignal are eager. effect runs during CD at least once; toSignal subscribes immediately. Rule: derive with computed, side effects only in effect. Moving to signals is mostly good news. A signal read in a template tells Angular to update that view, so no markForCheck. toSignal unsubscribes when its injection context is destroyed, and an effect is destroyed with it, so there is no cleanup code. And computed is lazy and memoised: if nobody reads it, the function never runs, and if the inputs did not change, it does not run again. Now the bad news, which is a performance point. effect and toSignal are eager. An effect runs during change detection whether or not anyone needs what it does. toSignal subscribes immediately, even if you never read the signal, so an HTTP request you forgot about still goes out. So the guidance: derive values with computed, because it only costs when read, and keep effect for real side effects. Do not use an effect to copy state, we covered that in the signals module.
