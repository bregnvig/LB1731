WeakMap as a cache

WeakMap<object, V>: entries vanish with their key object

Fits: a result that depends on the object only

Not used here: distance is already a memoised computed, and it depends on the location too. A long-lived cache would serve stale distances

The key must capture everything the value depends on

const labels = new WeakMap<Playground, string>();

function label(p: Playground) {
  let v = labels.get(p);
  if (!v) {
    v = `${p.name}, ${p.addressDescription}`;
    labels.set(p, v);
  }
  return v;
}
WeakMap<object, V>: keys are held weakly. When the key object is gone, the entry goes too. Good for: data computed per object that should live exactly as long as the object. Not used in the exercise: distance per row is already a memoised computed. A long-lived WeakMap would serve stale distances after the location changes. WeakRef: for optional references. A WeakMap is a map whose keys are objects held weakly. If nobody else references the key object, it is garbage collected and its entry disappears. So the cache cannot keep stale objects alive, which a normal Map would. It fits when you compute something from an object and the result is valid as long as that object exists: a parsed version, a formatted label, a layout measurement. Why we did not use it in the lab. The idea was to cache each playground's distance. But in this app the distance is already a computed in each list item, remembered per playground and location. It only re-runs when the location changes, and then you need a new distance anyway. A WeakMap keyed by playground would hand back the old distance after the location changed. A cache is only correct when the key captures everything the value depends on. So the bonus in the lab is content-visibility instead. WeakMap lives on this slide only.
